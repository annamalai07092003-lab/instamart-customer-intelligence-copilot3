# Instamart Customer Intelligence & Support Copilot

## Overview

This repository implements the four-part synthetic capstone using only local files, SQLite, pandas, NumPy, scikit-learn, joblib and the supplied offline `mock_llm.py`. All generated customer/order/ticket data are fictional; the brand framing, policies and INR amounts are for this exercise only. No network model calls or API keys are used.

The end-to-end pipeline audits and cleans the exports, stores clean tables in SQLite, builds RFM segments and a lapse model, triages support tickets with privacy guardrails, and provides policy retrieval plus a tool-using refund agent. The two supplied scripts, `generate_data.py` and `mock_llm.py`, are copied unmodified from the project brief.

Cleaning rules and effects:

1. Customers: trim and title-case city names, leaving exactly six cities; map gender variants to `male`, `female` or `unknown`; coerce age to numeric, mark values outside 10–100 missing, then fill missing ages with the median of the customer's city using `groupby(...).transform(...)`; parse signup dates. The 61 blank and 6 impossible ages are imputed (67 values total). There are no missing ages after cleaning.
2. Orders: parse `order_ts`; remove 119 exact duplicate rows (13,084 → 12,965); sort by timestamp and retain the latest record for each `order_id` (12,965 → 12,309, removing 656 earlier/pending records); convert amount to numeric and fill 120 invalid/missing amounts using product price × quantity × (1 − discount percentage / 100), rounded to two decimals; set 106 negative delivery times missing; fill missing delivery times only for completed orders using the median for that product category among completed orders. Cancelled orders remain without delivery times because they were not delivered.
3. Store the three clean CSVs in `data/clean/` and corresponding tables in `data/instamart.db`. Order timestamps are stored as `YYYY-MM-DD HH:MM:SS` text.

Clean customer reference counts: Pune 227, Delhi 210, Bengaluru 197, Chennai 191, Hyderabad 191, Mumbai 184; female 610, male 560, unknown 30. Clean orders: 12,309 rows, 11,110 completed and 1,199 cancelled, no pending rows, no missing amounts, zero missing delivery times for completed orders and 1,199 missing delivery times for cancelled orders. ### Lapse prediction

The cohort contains 1,156 customers with completed orders before the `2025-09-01` cutoff; 443 (38.32%) have no completed order during September. The stratified split has 924 training rows and 232 test rows. Features use only pre-cutoff orders and clean customer attributes; segment labels are not model features. Encoders, imputers and scalers are fitted within training/CV pipelines only; the test rows are never used to fit preprocessing or resampling. A feature-matrix assertion confirms no missing feature values.

The training-set scaler's learned mean for frequency is **8.115**, versus **8.029** for the full lapse cohort; they differ because the scaler is fitted on the training split only, not the entire cohort. Always predicting “not lapsed” yields test accuracy 61.6% and lapsed-class F1 0.000.

| Model | Best parameters | Best CV F1 | Test confusion matrix (actual rows 0,1; predicted columns 0,1) | Precision (lapsed) | Recall (lapsed) | F1 (lapsed) |
|---|---|---:|---|---:|---:|---:|
| Logistic regression | C=100 | 0.651 | `[[111, 32], [31, 58]]` | 0.644 | 0.652 | 0.648 |
| Random forest | max_depth=8, min_samples_leaf=10 | 0.687 | `[[111, 32], [32, 57]]` | 0.640 | 0.640 | 0.640 |

The selected persisted model is the random forest: it has the higher best cross-validated F1 (0.687), reaches test lapsed-class F1 0.640, and supports feature-importance summaries. Missing a genuinely lapsing customer loses a retention opportunity; incorrectly targeting a loyal customer wastes incentive budget and can annoy them. Since the costs are asymmetric, the team should review probability thresholds against campaign capacity rather than treating accuracy as the only objective. `outputs/lapse_model.joblib` is reloaded and its test predictions are asserted identical to the original model's predictions.

Class balancing duplicates lapsed training rows only, retaining the original test set. Logistic regression recall rises from 0.652 to 0.809; precision changes from 0.644 to 0.600 and F1 from 0.648 to 0.689. Recall moves most, so more at-risk customers are captured at the cost of more false-positive outreach.

Top random-forest features are monetary (0.278), frequency (0.277), recency (0.111), average delivery time (0.062) and average discount (0.053). The largest logistic coefficient signs are: frequency −1.697 (more frequent pre-cutoff orders reduce predicted lapse odds); Electronics as favourite category −1.135 (lower lapse odds relative to the dropped reference category); monetary +0.283 (higher spend raises predicted lapse odds conditional on the other features in this fitted model). Coefficients are model associations, not causal effects.

`outputs/retention_list.csv` contains the top ten predicted-lapse customers within the Premium segment; 1 of these ten truly lapsed in the September label window. **This list is illustrative and not a leakage-free evaluation** because the Premium flag is a post-hoc whole-window label that includes the September outcome window, even though the model features themselves use only pre-cutoff data.

## Part C

### Guardrails and redaction

Tickets are processed in raw-file order. Four blank tickets are marked `skipped_empty`; four tickets over the 400-token threshold (734 estimated tokens each) are marked `flagged_long` and never sent to the model. Redaction is applied in the required order: email → `[EMAIL]`, phone → `[PHONE]`, order ID → `[ORDER_ID]`. Across 164 tickets the substitutions are 55 emails, 91 phone numbers and 132 order IDs, **278 total**; rechecking the redacted text finds zero remaining matches. The model's user message contains only the redacted ticket text.

Every call is wrapped in a maximum-three-retry handler for `TransientLLMError`, with exponential backoff and jitter. Each full run resets `mock_llm`; all 19 transient failures per full run recover successfully. The zero-shot system prompt has no `EXAMPLES:` line; the few-shot prompt includes labelled billing, fraud and technical examples. Every response is parsed and validated: valid categories are `classified_json`; exactly one allowed category extracted from lowercase regex words is `classified_keyword`; all other responses, including valid JSON with an invalid category, are `flagged_invalid_output` and routed to human review.

| Zero-shot | 147 | 85.7% (126/147) | 10,180 | 69.25 |

The zero-shot confusion table is saved in `outputs/zero_shot_confusion.csv`: billing 38/38 correct, delivery 36/36 correct, fraud 23 correct and 11 predicted billing, technical 29 correct and 10 predicted billing. Few-shot adds 7,644 tokens overall (about 52.0 additional tokens per classified ticket) and improves accuracy by 14.3 percentage points, so it is worth the extra token cost when avoiding fraud/technical misroutes matters more than prompt cost. For low-risk, high-volume triage, zero-shot may be acceptable only with the same strict output validation and human-review fallback.

The zero-shot budget demo uses `TOKEN_BUDGET=6000` and records 64 `budget_exhausted` tickets in `outputs/triage_budget_demo.csv`. The budget is checked before each model call, so the final successful call may bring the accumulated total slightly above the threshold. The final `outputs/triage_results.csv` is a few-shot run with a 100,000-token budget and has 164 rows. Tickets skipped for emptiness, flagged long, invalid or budget-exhausted go to `human_review` with NORMAL priority; valid fraud tickets go to `security_team` with HIGH priority; otherwise Premium customers go to `premium_desk` with HIGH priority, and remaining tickets go to `support_queue` with NORMAL priority. Invalid outputs are never guessed; they are routed to a human.

## Part D

### Policy RAG

The five policy documents are split into 40-word chunks with 10-word overlap, producing 15 chunks: refund 4, delivery 3, escalation 3, payment 3 and privacy 2. `TfidfVectorizer` fits on these chunks; TF measures how often a term appears in a chunk and IDF downweights terms common across chunks. TF-IDF is lexical, so semantically equivalent questions with different wording may retrieve poorly. The `answer(question)` function retrieves three chunks and asks the offline `POLICY ASSISTANT` mock to answer only from those sources or use the required fallback.

| Evaluation | Expected document in top 3 | Expected fact in answer | Unanswerable questions use fallback |
|---|---:|---:|---:|
| 10-word overlap | 12/12 | 12/12 | 2/2 |
| Zero overlap | 12/12 | 10/12 | 2/2 |

With zero overlap, “What delivery time makes a completed order eligible for a full refund?” fails to include the expected fact: the qualifying threshold and refund consequence fall across a chunk boundary. Evaluation details are in `outputs/policy_eval_overlap10.csv` and `outputs/policy_eval_overlap0.csv`.

### Refund agent and safety limits

`TOOLS_SPEC` documents five tools and `TOOL_MAP` dispatches them to SQLite lookup, policy retrieval, refund calculation, issue and escalation functions. Only completed orders delivered in more than 45 minutes qualify for a full refund; amounts over INR 1,000 are escalated rather than automatically issued. Each issue/escalation appends a timestamped JSON line to `outputs/refund_ledger.jsonl`.

| Scenario | Status | Refund amount (INR) | Model calls | Tokens used |
|---|---|---:|---:|---:|
| S1 | REFUND | 128.25 | 5 | 1,012 |
| S2 | REFUND | 135.00 | 5 | 1,012 |
| S3 | ESCALATE | 1,999.00 | 5 | 999 |
| S4 | DENIED | 0.00 | 4 | 697 |
| S5 | DENIED | 0.00 | 3 | 406 |
| S6 | NOT_FOUND | 0.00 | 2 | 118 |
| S7 | FALLBACK_MAX_ITERATIONS | 0.00 | 6 | 3,138 |

Stop-safely demonstrations: S1 with token limit 200 ends `FALLBACK_TOKEN_LIMIT`; a run with `time_limit_seconds=0` ends `FALLBACK_TIMEOUT` before the first model call. S7 reaches six model calls and safely ends `FALLBACK_MAX_ITERATIONS` under the default 6,000-token limit. Fallbacks include a human-handoff summary and preserve completed steps.

The crash/resume demonstration crashes after saving the second tool observation, then resumes from `state/S1_CRASH_RESUME.json`. Across both parts, the tools execute exactly once each and in this order: `get_order`, `search_policy`, `calculate_refund`, `issue_refund`. The resumed result is `REFUND: INR 128.25 issued.` and no completed tool action is repeated. See `outputs/agent_runs.jsonl`, `outputs/agent_scenario_results.csv`, `outputs/agent_safety_demos.json` and `state/`.

ReAct makes a new model call after each observation (five calls for S1, three for S5 and two for S6), so it uses more round trips and usually more tokens than a plan-and-execute approach that requests the whole tool sequence once and replans only on error. ReAct reacts directly to unexpected observations such as a missing order or cancelled order and can stop before issuing a refund. A one-shot plan can be cheaper but risks executing stale steps if an observation differs from expectations. For this refund workflow, use ReAct with hard tool-side policy checks, token/time/iteration limits and human fallback; tool-side validation remains essential regardless of planning style.

## Limitations and Next Steps

- All data, tickets, policies and model behavior are synthetic; results are not real customer outcomes or operational policy.
- The offline mock is deterministic and does not measure real LLM accuracy, latency or cost. TF-IDF can miss semantic matches; production use would need stronger retrieval evaluation and policy-version controls.
- The lapse label covers a single month and class balance is imperfect. Monitor precision/recall at campaign capacity and validate on a later time-based holdout before deployment.
- **The Premium flag is a post-hoc whole-window label, so the retention list is illustrative and not a leakage-free evaluation.**
- A production refund workflow should add authentication, idempotency keys, audit controls, currency rounding rules, explicit delivery-date validation, and human approval for high-value refunds. The current assignment assumes requests are inside the seven-day window.
